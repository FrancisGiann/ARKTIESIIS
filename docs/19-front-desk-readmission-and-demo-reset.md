# Front-desk intake, return evaluation, and demo data

## Required paper intake

Only front-desk staff can create a paper pre-enrollment record at `/pre-enrollments`. Front desk can save incomplete drafts and correct entries before annual enrollment starts. A Ready record requires the paper identity and academic details, a complete 12-digit LRN, a valid student contact email, and the other required paper fields. The authenticated staff actor is recorded as the creator or editor; the separately transcribed paper receiver remains a paper-form value. Draft and Ready changes use optimistic revisions and append-only history. After conversion starts, the paper entry is read-only.

The front-desk form captures the full student profile needed by the existing master record, including email, birth date, gender, phone, five-component student and emergency-contact addresses, family details, birthplace, and Facebook name. Legacy free-text addresses remain authoritative until a user explicitly selects replacement. Structured parts and the compatibility formatted field are stored together. An unrelated profile correction never replaces a legacy address.

Registrar staff can find and correct Ready records and start an annual enrollment from a saved source. Database administrators can review source records and history but cannot edit them. Other roles have no access. The enrollment wizard requires the source id and version; a direct or unsourced new annual intake is rejected. It displays saved identity and the review snapshot, defaults to an existing student when the LRN identifies one, and requires the registrar to explicitly approve any returning-profile corrections. Each address is one approval unit: formatted and structured values are updated together. Active and unconsumed pending email reservations are checked under transaction locks; a registrar-approved email change consumes outstanding login/recovery tokens, invalidates sessions, and writes a user-scoped audit event. Paper receipt counts never mark the physical checklist as verified.

The registrar still chooses the actual voucher, school year/grade where allowed, term, section, enrollment date, and placement/finance classification. Preferences written on paper are not translated into enrollment classifications. Saving a paper entry alone creates no master student, login, student number, annual record, term placement, assessment, or charge. Annual creation locks and revalidates the source, accepted evaluation if any, and returning-student snapshot, then commits the annual record, source link, approved profile changes, revisions, and audit events atomically. Identical retries return the same annual record; changed or stale versions conflict. First confirmation revalidates a readmission decision. Source-less historical annual records can continue through existing later-term workflows.

## Return evaluation

The registrar starts **Evaluate return** from Student records after searching by name or LRN. For an existing student, the evaluation is saved in the student record alongside the Academics view; prior statuses, revisions, and before/after history remain available there. Search results also show unlinked evaluations matching the applicant's name or LRN, so a registrar can resume them from the same workspace. If no student record exists, the registrar can start or resume a review by LRN and minimal identity without creating a student, account, or enrollment. Older `/registrar/readmissions` bookmarks redirect to the matching student record or the unlinked evaluation inside Student records.

For a saved student, **Evaluate return** appears only when the saved record contains either a latest recorded dropped/transferred departure or confirmed prior participation followed by at least one full school-year gap before the configured current school year. A departure uses its effective term; affected later placements do not move the departure point, and the recorded departure takes precedence over that annual record's pending or enrolled intake flag. A newer or same-term active/pending placement, a newer unresolved intake, previous-year continuous participation, or an older departure followed by later participation does not expose the action. The evaluation target school year does not establish eligibility. A missing current-year setup prevents gap detection, and profile status, payment state, missing grades, or missing history alone does not establish an interruption. Same-year reactivation remains unavailable.

Inside a linked evaluation, staff can review the live saved academic history alongside the saved evaluation findings and revision history. The context shows the latest chronologically supported enrollment summary, each recorded enrollment's grade/section/year/term/status, and its subject codes/names with recorded grading periods, marks, and remarks. Numeric zero is shown as a mark; missing marks stay missing. These are recorded assignments and grades, not an automatic subject-completion decision or a source of grade writes. A recorded departure date/type is shown separately, and the latest enrollment label does not claim when or why the learner stopped. The full Academics view remains available. Unlinked applicants continue to use the required prior-progress and evidence fields for paper-record review.

A missing historic student master can be reviewed by LRN and minimal identity. That path creates no student, account, or enrollment and cannot be used when the LRN already belongs to a saved student. Only registrar conversion of the fresh paper entry into annual enrollment allocates a new student number.

The registrar records prior progress, evidence inspected, the curriculum comparison, required subjects, subject availability, reason, and decision. Stored academic history and inspected paper records are review sources; Form 137 can support review but is not a newly required verified document. The application does not infer curriculum equivalency or make an admissions decision. Acceptance requires the registrar to mark the curriculum comparison Resolved, identify the required subjects, and confirm their availability. Evaluation acceptance binds the LRN, optional existing student, school year, target grade, and evaluation revision. Staff-only history keeps bounded before/after snapshots of each saved evaluation and decision reason, so reopening a review does not erase its prior findings. Revisions reopen the decision and invalidate paper/conversion bindings. Once an annual enrollment has started, the evaluation is read-only. Same-year reactivation is outside this workflow.

After acceptance, front desk starts a fresh paper intake and receives only the evaluation's identity, LRN, school year, grade, and revision needed to bind that paper record. Academic progress, evidence, availability notes, curriculum findings, and decision reasons remain in the registrar/admin evaluation view. The conversion service checks the binding again, and first annual confirmation checks that the same accepted revision is still current.

## Resetting and reseeding a disposable student cohort

`npm run demo:reset-students-mariadb` is a guarded, MariaDB-only maintenance CLI. It defaults to a read-only inventory. It never drops a database, disables foreign-key checks, or deletes retained staff accounts, academic setup, term ordering/reviews, finance fee definitions, and physical requirement definitions. It deletes the student cohort and dependent student data, including pre-enrollment and readmission history, annual/term/grade/document/workbook/finance activity, student-only login tokens, and dummy audit history. It only removes uploaded files whose exact database references were inventoried and whose paths pass the helper's UUID and storage-root checks.

For a hosted reset, use the host's normal maintenance controls and private environment configuration; there is no public reset endpoint. Apply migration `v2.016` before deploying the code that honors maintenance mode. Set `APP_MAINTENANCE_MODE=true` in the application process environment, restart the normal entry point, and verify public and write routes respond with maintenance responses before continuing. This entry point starts no database schema checks or application workers while maintenance is active. Pause any separately scheduled writer as well. If this cannot be verified, stop before reset.

Create a private, checksummed database backup and uploaded-file archive outside the checkout and public web root. Restore both into a disposable MariaDB/file fixture and verify the restore before the hosted reset. Run the CLI without `--apply`, inspect the exact cohort, dependency counts, retained-table fingerprints, endpoint/server identity, and referenced file inventory, then set the matching allowlist, preview digest, exact student counts, backup confirmations, and private resumable manifest path. `--apply` rechecks the plan and deletes within one transaction. For host-managed files, use `--database-only`; the CLI records a private pending-file manifest. Remove only the exact listed files in the host file manager, verify each result, then run `--mark-files-removed` with the manifest digest and explicit confirmation. For local files, use the exact storage-root mode and `--resume-files` after an interrupted cleanup. Do not seed while the manifest is pending.

After the reset is complete, `npm run demo:seed-students-mariadb -- --dry-run` verifies the exact endpoint, v2.016 schema, completed reset manifest, backups, retained setup counts, and required 2026–2027 sections and finance schedules. Apply requires explicit database confirmation, active maintenance, outbound email disabled, and a new private credential-artifact path outside the checkout. The maintained seeder uses the existing front-desk, registrar, annual-enrollment, and finance services; it sends no email and creates no document verification events. It produces new-applicant draft/Ready examples, a Ready record in the retained 2026–2027 setup, a future-year continuing record, accepted and declined return-evaluation cases, and unpaid/partial/settled modern-fee examples. Student passwords are generated at runtime and stored only in the private artifact; staff credentials and retained setup remain unchanged.

Before leaving maintenance mode, verify the reset marker and seed marker, expected demo record counts, staff/setup fingerprints, both track families and receipt rows, approved evaluation binding, student finance balances, and login/2FA behavior. If reset, file cleanup, or seed verification fails, keep maintenance active and restore both database and uploaded files from the private backups. Do not use the legacy SQL Server reset script for MariaDB and do not run this workflow against a school dataset without a separate explicit authorization and reviewed inventory.
