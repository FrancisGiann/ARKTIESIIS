# Gemini-Assisted Document Precheck

## Document workflow

1. The uploader selects a permitted document type and the server checks role, filename/type/signature, and configured size before private storage as `pending`. A previous-school report-card scan is accepted only for the uploader's linked record and enters the same bounded worker queue as a digital enrollment submission.
2. A bounded background worker atomically claims pending rows and sends the stored PDF, JPEG, or PNG bytes inline to Google Gemini using the built-in Node.js `fetch` API. The app does not use the Gemini Files API or an SDK package.
3. Gemini returns a strict structured response containing only the requested visible fields. The server bounds and sanitizes these values, compares the extracted student name against the linked student record, and stores a small staff-only precheck summary. The field matcher supports ordinary and surname-first name order, including one surname comma, while rejecting malformed comma lists and explicit multi-person text. Extracted full-page text is not saved.
4. Good Moral, PSA, and active previous-school report-card scan prechecks remain `needs_review` even when configured checks pass. A registrar or database administrator must inspect the source file and manually verify, request a correction, or reject it. The scan uses a name-and-format precheck plus the enrollment-submission checklist; the precheck never extracts grades. Only a staff `verified` decision sets a document to `valid`; report-card decisions never update grade records.
5. The detail page shows authorized staff the extracted fields, server-side name comparison, configured precheck outcome, source preview, and review checklist. Students see operational status, applicable correction instructions, and rejection reasons for their own Good Moral, student-uploaded PSA, and active student-origin report-card submissions. Staff-origin PSA correction instructions and reasons remain staff-only.

If a Good Moral, PSA, or active report-card precheck ends with a transient Gemini timeout, network error, or API error after the file-format check passed, a registrar or database administrator can retry it from the existing detail page. The retry reuses the stored file, preserves previous validation rows, and enters the normal bounded worker queue. Each upload allows at most three total Gemini attempts (the original attempt plus two staff retries). Active staff authorization, retry eligibility, the attempt limit, the active archive flag, and the absence of a final decision are rechecked transactionally. A retry never records a verification or rejection decision.

Authorized staff may also send a temporary Form 137 scan to Gemini for student-name and possible school-name suggestions. The service validates the file and sends its multipart buffer directly to Gemini in memory. It does not create a temporary file, document row, validation row, or audit entry. The request buffer is cleared after processing, and the response is private and no-store. Only the human-recorded physical status and instruction are retained. Gemini suggestions do not set that status.

Previous-school report cards have two distinct enrollment-requirement channels: the student's private digital scan submission and staff-recorded receipt/status of the paper copy brought to school. The staff-only paper status history is stored separately by V2 migration `003_previous_school_report_card_physical_status.sql`; forward-only migration `004_previous_school_report_card_status_constraint.sql` gives its status check a stable name. Its prototype statuses are pending, received, verified, correction, and rejected; staff notes/history are not shown to students. These labels and decision criteria need school review before deployment. Neither channel edits, supplies, or publishes current grades. Form 137 remains a separate staff-only physical-record workflow.

## Gemini configuration and bounds

Set `GEMINI_API_KEY` in the private `.env`. Without a key, digital submissions remain available for staff review with an unavailable precheck; Form 137 scans return a safe unavailable result. The default `GEMINI_MODEL` is `gemini-3.8-flash`; set a valid Gemini model identifier to change it. `GEMINI_TIMEOUT_MS` defaults to 45 seconds and accepts 1–120 seconds. `DOCUMENT_PROCESSING_CONCURRENCY` defaults to two workers and accepts one through four. Upload size defaults to 10 MB via `MAX_UPLOAD_MB`. Inline Gemini request content is capped at 14 MiB and the response at 32 KiB.

Only PDF, JPEG, and PNG files are sent. For stored files, the worker opens the private file once with no-follow semantics where supported, checks the opened handle, validates the file signature, and reads a bounded byte count from that same handle. API keys are sent in the `x-goog-api-key` header. API errors and response bodies are not logged or shown. Tests use mocked `fetch`; they never make a live API request.

This integration sends document bytes, which can contain student personal data, to Google Gemini for field extraction. The application does not claim control over the provider's processing or retention policies; operators must configure the provider account and privacy terms appropriately before deployment.

## Configured extraction and precheck

- **Good Moral Certificate:** Gemini is asked to copy the visible student name, issuing-school name, an affirmative title or substantive character statement, and a short description of surrounding certificate content. The server requires a linked-name match, nonempty school name, context clues that pass configured negation and uncertainty patterns, a description of visible certificate components, and a matching supported file format for a precheck pass. Isolated name and school text are insufficient. These bounded text clues cannot interpret every sentence; staff must inspect and assess the meaning of every source. No fixed school template or logo is required.
- **PSA birth certificate:** Gemini is asked for the visible student name only. A school-name field does not apply.
- **Active student-uploaded report card:** Gemini is asked for the visible student name only. Its response schema contains no grade, mark, subject, attendance, or academic-result fields. The server checks the declared PDF/JPEG/PNG format. The precheck does not publish or change grades.
- **Form 137 temporary scan:** Gemini suggests the visible student name and a possible printed school name. Suggestions are returned to staff in a bounded transient response only.
- **All files:** extension, declared MIME type, stored MIME type, and file signature must agree with PDF/JPEG/PNG.

The precheck is deliberately conservative, but model output can still be inaccurate. No representative school samples or independent accuracy study have been used to measure extraction accuracy. A precheck pass is not a whole-document completeness check, proof that the school issued the file, proof of document authenticity, or an acceptance decision. Gemini does not detect forgery, verify signatures or seals, or conduct forensic analysis. Staff must inspect every submitted page. No page completeness or institution-specific required-field rules are automated. The updated field matcher and Good Moral evidence rules apply to new processing and eligible retries; existing validation rows and their version-2 summaries remain historical and are not rewritten.

### Bounded extraction evaluation

`npm run evaluate:document-precheck` validates the labelled fixture manifest, PDF/JPEG/PNG signatures, sample paths, file sizes, and expected labels, then reports a local dry run with zero provider calls. The default manifest and six deterministic fictional PDFs live in `tests/fixtures/document-precheck/`. A live evaluation requires the explicit `--live` flag and a private `GEMINI_API_KEY` in the environment or `.env`:

```bash
npm run evaluate:document-precheck -- --live
```

The evaluator accepts only a bounded version-1 JSON manifest with `sampleType` set to `synthetic` or `representative`, up to 12 labelled samples, and direct filenames contained in the selected sample root. It validates every label and sample file before creating a provider request, reads each file without following symlinks, checks the declared type against the extension and file signature, caps each file at the Gemini inline limit and the total sample bytes at 40 MiB, and makes calls sequentially with a 45-second per-call timeout and a six-minute total limit. Optional `--manifest <path>` and `--root <directory>` flags select another approved local set. These limits are for a small, repeatable evaluation and are independent of application database workflows.

The aggregate JSON report contains extraction status counts, normalized exact-name extraction counts, the production linked-name false-positive and false-negative rates, precheck-code agreement, abstentions/unavailable results, skipped deadline samples, and latency. Exact-name comparison normalizes case, diacritics, and punctuation; it is not a character-for-character comparison. Each linked-name rate includes its numerator and determinate-result denominator; unavailable results and skipped samples are counted separately for expected matches and nonmatches. A representative accuracy measurement is marked only when the manifest is representative and at least one result was extracted. Reports include the evaluation date and model but never sample paths, IDs, extracted or expected names, document fields, bytes, provider errors, or keys. The checked-in samples are synthetic and demonstrate measurement plumbing only; they do not establish representative school accuracy or an accuracy target. Tests use deterministic mocked responses and do not make live requests.

A single live run against the six fictional fixtures completed on 2026-10-08 with `gemini-3.5-flash-lite`; its aggregate report is [recorded here](document-precheck-evaluation-synthetic.json). It matched all five labelled visible names and all six expected precheck codes. The linked-name confusion matrix was TP 4, FN 0, FP 0, TN 2. These are synthetic fixture results only, not a representative school accuracy estimate.

Legacy validation rows without `precheckVersion: 2` are identified as **Legacy OCR-only** and always report that Gemini was not run. Their stored OCR text and suggestions remain visible only to authorized staff as historical supporting material; they cannot produce a Gemini pass.

## Source-inspection checklist and decisions

Before recording `verified`, authorized staff must attest that they inspected the source file and confirmed. The report-card checklist is provisional; it only records human observations and is separate from grade publication:

- For Good Moral: the linked student name is visible and legible; school-name text is visible and legible; Good Moral title or character statement and surrounding certificate content are present; the selected document type matches the file; and all submitted pages are readable and complete.
- For PSA: the linked student name is visible and legible; the selected document type matches the file; and all submitted pages are readable and complete.
- For a previous-school report-card scan: learner name and student number match the linked record; a grading period or school year is identified; the selected type matches the file; and all submitted pages are readable and complete. This submission checklist is unrelated to current-grade entry.

The checklist records reviewer observations. It does not establish authenticity or school legitimacy. Checklist schema version 2 adds the Good Moral context item; stored version 1 history retains its original wording. Migration `008_document_verification_checklist.sql` adds nullable checklist storage, so older decisions remain unknown rather than inferred.

`pending` means field extraction is queued, `processing` means a worker has claimed it, `needs_review` means staff review is required, and `failed` means the automated process could not finish. Unavailable extraction never produces a pass. Legacy OCR rows are labeled separately. A staff reason is required when verifying despite a warning or unavailable result. Form 137 uses the separate physical status history (`pending`, `received`, `verified`, `correction`, `rejected`); a scan suggestion never changes it.

## Access and storage boundary

Students may upload Good Moral, PSA, and previous-school report-card scans only for their own linked record. They may view, preview, download, and correct an active student-origin scan only after staff requests a correction. The V2 lifecycle flag keeps pre-lifecycle report-card archive rows staff-only and read-only, including for direct URL access; archives are excluded from worker, retry, and student history queries. Active scans receive a limited visible-name and file-format precheck and mandatory staff review; they do not alter grades. Students see only the latest status/date for their own paper-copy status and never staff notes/history. Staff access to the staff student-document workspace remains restricted to registrar and database administrator roles. Students may view their own submissions and student/staff PSA files under the existing access rules. Form 137 remains staff-only; no persistent Form 137 upload is created. Finance users have no document access. Stored digital files remain private; corrected permitted uploads are separate linked submissions. A student or staff member may start a new original Good Moral or PSA submission only when the latest submission for that student and type is rejected; a newer pending, processing, valid, needs-review, or failed submission keeps new-original upload blocked. Rejected rows and review history remain available. Correction-requested reuploads continue as linked submissions. Registrars and database administrators can permanently delete an individual active Good Moral, PSA, or student-origin report-card submission and its stored file and review history; the deletion itself remains in the staff audit log without document contents or review reasons. A version with a corrected submission cannot be deleted until its latest correction is deleted. Report-card archives and Form 137 records cannot use this deletion action. No school retention period or automatic deletion policy is configured.

Staff can preview an image inline on the detail page with zoom and pan controls. PDF preview uses the authorized same-origin route. History preview controls use the MIME type returned by the server rather than deriving it from the filename. Preview and download routes re-check role and ownership, use private no-store headers, and never expose the private storage path.

Tesseract and Poppler are no longer wired into active document processing. The old local OCR service, synthetic OCR fixtures, and historical runtime report remain as inactive legacy artifacts only; they are not required to run the application. Migration `005_local_ocr_processor_default.sql` remains applied as historical schema history, while active processing explicitly writes the `Gemini field extraction` processor label and leaves old validation rows unchanged.

## Verification evidence and limits

Automated tests cover structured request construction, PDF/JPEG/PNG validation, missing key, blocked/malformed/oversized responses, timeout, privacy-safe errors, field sanitization, linked-name comparison, conservative Good Moral criteria, symlink rejection, bounded processing, staff-only findings, authorized previews, and transient Form 137 behavior. Tests use synthetic documents and mocked Gemini responses. They do not measure model accuracy, use real student documents, contact Gemini, or establish a live SQL Server/provider integration.

## SSHS E-Class Record grade import

The registrar-only direct grade import accepts the corrected SSHS E-Class Record for SY 2026–2027 as a fallback. Assigned teachers can also submit one corrected workbook for their term/section/subject assignment. Both paths read cached Term 1, Term 2, Term 3, and Final Grade values and do not recalculate formulas. Blank formula caches make the affected learner row ineligible; recalculate and save the workbook in Excel before uploading it again. The direct registrar path uses the workbook in memory and never stores it. The teacher path retains the original XLSX and parsed snapshot privately until the documented archival retention policy is defined.

Before upload, a registrar chooses an existing 2026–2027 school-year, grade-level, section, and subject context. The preview compares this selection with the workbook context and matches learners by a unique 12-digit LRN to active students and exactly one existing enrollment and assigned subject. Missing/ambiguous matches, incomplete cached grades, duplicate workbook LRNs, and context mismatches are excluded for roster correction and reupload. The preview shows student number and database name; an LRN match with a name difference requires a registrar review checkbox and reason. Every row must be explicitly included. Different existing grades are kept unless the registrar chooses replacement with a reason; equal values are left unchanged.

Preview data is private and tied to the uploader's session; transient previews become inaccessible after 30 minutes and are deleted when confirmation completes. Expired rows are removed opportunistically on the next grade-import request. No timed SQL cleanup job is configured. Teacher submission stores a private original workbook and a non-sensitive parsed snapshot; teacher submit does not write grades. Registrar approval rechecks the active assignment, student identity, enrollment, subject, roster, and existing grade state in a serializable SQL Server transaction. The audit record contains counts and recorded review reasons, not raw LRNs, grade values, or workbook bytes. Migration `007_student_lrn.sql` adds nullable unique LRNs for existing rows; new student records require an LRN. Registrars may backfill a blank LRN, while only database administrators may change a recorded value. Migration `009_teacher_grade_submissions.sql` adds teacher assignments and durable submission/history storage.

The registrar may approve, request correction, or reject a pending workbook. A correction request permits a new revision; submissions and decision events remain in history. Revoking an assignment blocks further teacher access and registrar approval. Deactivating the submitting teacher blocks their access/revision, but does not discard a durable pending submission; registrar review remains possible if the assignment stays active. Approval detects changes to roster/enrollment/subject identities or grade state and writes no grades if the snapshot conflicts.

This import's fixed 0–100 range and four period names are implementation constraints for the approved workbook, not an institution-wide grading policy. The Phase 10 thesis implementation gate is separate from the school-adoption gate: the selected manual checklist and status labels still require institution signoff before school deployment.
